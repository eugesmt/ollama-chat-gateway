# Приватный локальный LLM-сервис

Проект предоставляет HTTP-обвязку над Ollama. Go-приложение принимает задания от клиентов, ограничивает входные данные и частоту запросов, ставит задания в bounded queue, отправляет их worker-ам, а результат отдаёт клиенту потоково через SSE.

Ollama здесь является движком инференса. Docker Compose не заменяет Go API и не требует открывать порт Ollama для внешней сети.

## Архитектура

    браузер / curl / устройство 1 ─┐
                                    ├─ HTTP :8080 ─ Go app
    браузер / curl / устройство 2 ─┘                  │
                                      rate limit       │
                                      queue + workers  │
                                                       ▼
                                          Ollama :11434
                                                       │
                                                   модель

При 'WORKER_COUNT=1' одновременно выполняется одно задание, остальные находятся в очереди. При увеличении значения нужно учитывать, что параллельная генерация потребляет дополнительную память модели и KV-cache. 'QUEUE_SIZE' ограничивает число ожидающих заданий; при переполнении API возвращает '503 queue_full'.

Состояние job предполагается хранить в памяти приложения, а 'JOB_TTL' задаёт срок удаления завершённых job. Перезапуск контейнера очищает очередь и историю job.

## Переменные окружения

Скопируйте шаблон и замените секрет:

    cp .env.example .env

Основные настройки:

| Переменная | Назначение | Значение по умолчанию |
| --- | --- | --- |
| 'LISTEN_ADDR' | адрес HTTP-сервера | ':8080' |
| 'OLLAMA_URL' | URL Ollama | зависит от способа запуска |
| 'OLLAMA_MODEL' | имя загруженной модели | 'llama3.2:3b' |
| 'WORKER_COUNT' | число workers | '1' |
| 'QUEUE_SIZE' | размер очереди ожидания | '8' |
| 'MAX_INPUT_CHARS' | максимум суммы символов всей переданной истории | '8000' |
| 'MAX_MESSAGES' | максимум сообщений в истории чата | '20' |
| 'MAX_OUTPUT_TOKENS' | максимум генерируемых токенов | '512' |
| 'NUM_CTX' | контекст модели | '4096' |
| 'RATE_LIMIT_RPM' | запросов в минуту на IP | '5' |
| 'JOB_TTL' | время хранения job | '15m' |
| 'REQUEST_TIMEOUT' | timeout вызова Ollama | '2m' |
| 'API_KEY' | ключ доступа к API | заменить на случайный |

Для обычных HTTP-запросов используется 'Authorization: Bearer ...' или 'X-API-Key: ...'. Браузерный 'EventSource' не умеет добавлять заголовки, поэтому UI передаёт ключ только на SSE-маршруте как 'api_key' query-параметр. На остальных API-маршрутах query-ключ отвергается.

## Запуск с уже установленной Ollama

Сначала убедитесь, что Ollama запущена на хосте и модель доступна:

    ollama pull llama3.2:3b
    ollama list

Для запуска Go-сервера непосредственно на хосте:

    export OLLAMA_URL=http://127.0.0.1:11434
    export OLLAMA_MODEL=llama3.2:3b
    export API_KEY='замените-на-длинный-случайный-ключ'
    make run

Для запуска приложения в контейнере при Ollama на хосте:

    cp .env.example .env
    # В .env укажите API_KEY и модель.
    docker compose up -d --build

Compose использует 'host.docker.internal:11434' как адрес Ollama из контейнера. На Linux это имя добавляется через 'extra_hosts'. Если Ollama слушает только '127.0.0.1', контейнер не сможет обратиться к ней через host gateway. В таком случае настройте Ollama на прослушивание нужного интерфейса, например через 'OLLAMA_HOST=0.0.0.0:11434', и ограничьте порт firewall-ом так, чтобы доступ был только от Docker bridge или доверенной LAN. Не публикуйте '11434' в интернет.

## Запуск Ollama в Compose

Сервис Ollama находится в профиле 'ollama', поэтому он не запускается без явного указания профиля. Модели сохраняются в именованном volume 'ollama_models'.

    cp .env.example .env
    export API_KEY='замените-на-длинный-случайный-ключ'
    OLLAMA_URL=http://ollama:11434 docker compose --profile ollama up -d --build
    docker compose exec ollama ollama pull llama3.2:3b

В этом режиме порт Ollama не публикуется на хост: он доступен только внутри compose-сети. Наружу публикуется только 'APP_PORT' приложения, по умолчанию '8080'.

Проверка состояния контейнеров:

    docker compose ps
    curl http://127.0.0.1:8080/healthz

Если в '.env' задан 'OLLAMA_URL=http://ollama:11434', этот адрес будет использоваться и без profile. Для сценария host Ollama оставьте 'http://host.docker.internal:11434' при контейнерном запуске или 'http://127.0.0.1:11434' при запуске Go напрямую.

## Сетевой доступ с двух устройств

Сначала проверьте сервис с самого сервера:

    curl http://127.0.0.1:8080/healthz

Затем узнайте LAN-адрес сервера и откройте с другого компьютера или телефона:

    http://SERVER_LAN_IP:8080/

Разрешайте в firewall только TCP-порт '8080' из доверенной домашней сети. Для доступа извне используйте VPN (например, WireGuard/Tailscale) или защищённый reverse proxy с TLS и авторизацией. Не пробрасывайте в интернет ни '11434', ни сервис без API key/rate limit.

UI встроен в Go-бинарник и доступен в корне ('/'); API-маршруты имеют приоритет и не перекрываются static assets.

## API и потоковая выдача

Ожидаемый контракт, на который рассчитаны скрипты:

1. 'GET /healthz' возвращает '200 OK'.
2. 'POST /api/v1/jobs' принимает JSON:

        {
          "messages": [
            {"role": "user", "content": "Объясни, что такое Docker"}
          ],
          "model": "llama3.2:3b"
        }

   Ответ создаёт job и возвращает его идентификатор:

        {
          "job_id": "job_123",
          "status": "queued",
          "events_url": "/api/v1/jobs/job_123/events"
        }

3. 'GET /api/v1/jobs/{job_id}/events' держит SSE-соединение. Возможные события:

        event: status
        data: {"status":"queued","queue_position":1}

        event: status
        data: {"status":"running","wait_ms":42}

        event: token
        data: {"text":"Docker"}

        event: done
        data: {"status":"completed","wait_ms":42,"ttft_ms":120,"duration_ms":900,"total_ms":942}

    Событие 'done' содержит те же timing-поля. При ошибке backend отправляет
    'error' с полем 'error', а затем 'done' со статусом 'failed'.
    При reconnect заголовок 'Last-Event-ID' продолжает поток после уже
    полученного события; неизвестный ID приводит к безопасному полному replay.

Пример ручной проверки:

    export API_KEY='ваш-ключ'
    curl -fsS -H "X-API-Key: ${API_KEY}" \
      -H 'Content-Type: application/json' \
      -d '{"messages":[{"role":"user","content":"Привет! Ответь кратко."}]}' \
      http://127.0.0.1:8080/api/v1/jobs

    curl -N -H "X-API-Key: ${API_KEY}" \
      http://127.0.0.1:8080/api/v1/jobs/JOB_ID/events

Если фактическая реализация использует другие пути или формат ответа, передайте их скриптам через 'CHAT_PATH', 'JOB_EVENTS_PATH_PREFIX' и 'HEALTH_PATH' или скорректируйте примеры API.

## Скрипты проверки

Скрипты используют только Bash и curl; для разбора 'job_id' 'jq' не требуется.

    export API_KEY='ваш-ключ'
    ./scripts/smoke.sh
    COUNT=6 ./scripts/load.sh

Переменные скриптов:

    BASE_URL=http://192.168.1.50:8080
    OLLAMA_MODEL=llama3.2:3b
    COUNT=4
    REQUEST_TIMEOUT_SECONDS=300

'smoke.sh' проверяет health, создаёт одну job, читает SSE до маркера завершения. 'load.sh' одновременно создаёт несколько job и параллельно читает их SSE. Эти команды являются тестовым инструментом и сами по себе не доказывают успешность работы: результат необходимо получить после запуска системы.

## План проверки и ожидаемые результаты

1. Health: 'GET /healthz' отвечает '200'.
2. Одиночный чат: job получает 'job_id', затем приходят 'queued', 'running', фрагменты 'token' и финальное событие.
3. Два устройства: оба клиента получают только свои ответы и не видят поток другого job.
4. Очередь: при 'WORKER_COUNT=1' второй длинный запрос остаётся 'queued', пока первый выполняется.
5. Параллельная нагрузка: 'COUNT=4' создаёт несколько job; при переполнении очереди часть запросов получает '503 queue_full', а не зависает бесконечно.
6. Rate limit: после превышения 'RATE_LIMIT_RPM' API отвечает '429' и сообщает о необходимости повторить запрос позже.
7. Ограничения контекста: слишком длинный вход или слишком большая история отклоняются до обращения к Ollama ('400'/'413', согласно реализации).
8. Timeout: недоступная или медленная Ollama приводит к завершению job с понятной ошибкой, а worker освобождается.
9. Безопасность: порт '11434' не опубликован Compose, а доступ к '8080' разрешён только из LAN/VPN.

Фактические результаты этих проверок здесь не заявляются: их нужно выполнить на сервере с конкретной моделью, CPU/GPU и сетевой конфигурацией.

## Troubleshooting

**'connection refused' к Ollama.** Проверьте 'ollama serve', 'curl http://127.0.0.1:11434/api/tags', имя модели и 'OLLAMA_URL'. Для контейнерного app убедитесь, что host Ollama доступна из Docker gateway, либо используйте compose profile.

**Модель не найдена.** Выполните 'ollama pull ${OLLAMA_MODEL}' на host или 'docker compose exec ollama ollama pull ${OLLAMA_MODEL}' для compose-сервиса.

**Контейнер app unhealthy.** Посмотрите 'docker compose logs app', проверьте '/healthz', порт '8080' и наличие бинарника, собранного из './cmd/server'.

**Все job долго стоят в очереди.** Это ожидаемо при 'WORKER_COUNT=1' и длинной генерации. Проверьте GPU/RAM, 'REQUEST_TIMEOUT', 'MAX_OUTPUT_TOKENS' и размер контекста. Увеличивать workers следует только после замера памяти.

**Второе устройство не открывает UI.** Проверьте LAN IP, firewall, что приложение слушает ':8080', и что клиент находится в той же сети или VPN. Не используйте '127.0.0.1' на втором устройстве: это будет само второе устройство.

**SSE обрывается через reverse proxy.** Отключите buffering для SSE, увеличьте read timeout и убедитесь, что proxy передаёт 'text/event-stream' и не закрывает idle-соединение. Для первичной проверки используйте прямой адрес ':8080'.
